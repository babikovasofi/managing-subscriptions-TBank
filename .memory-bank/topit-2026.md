## Как устроен проект

| Где | Что находится |
| --- | --- |
| [data/](../data/) | Генератор клиентов, операций и размеченных сценариев. Справочники мерчантов и подписок. Результаты генерации идут в игнорируемую папку `data/output/`. |
| [ml/](../ml/) | Признаки по клиенту и мерчанту, отбор правилами, LightGBM, отдельная эвристика пробного периода, прогноз даты, статусы, аналитика и уведомления. |
| [api/](../api/) | FastAPI и SQLite. `init_db.py` запускает пайплайн и сохраняет результаты. API читает кэш, ручные подписки и действия пользователя. |
| [web/](../web/) | Next.js, TypeScript и Tailwind. Список подписок, детали, уведомления, аналитика и ручное добавление. В `web/design/` лежат макеты первой итерации. |
| [docs/](../docs/) | ТЗ ТОПИТ, контракт и примеры API, отчёт об интеграции и история майского MVP. |

Поток данных — генерация транзакций и разметки → обучение → расчёт подписок → SQLite → FastAPI → мобильный веб-интерфейс. Фронт сейчас открывает фиксированный профиль `scripted_04`, хотя API отдаёт список клиентов.

## Сверка требований кейса

| Требование | Что есть и что нужно проверить или добавить |
| --- | --- |
| Серверный модуль и поиск подписок на тестовой истории | Есть гибрид правил и LightGBM по парам клиент–мерчант, плюс эвристика trial. Данные синтетические. |
| Отличать подписки от коммуналки, аренды и переводов | Есть арендные и другие сложные отрицательные сценарии и фильтры. В локальном прогоне детектор отфильтровал все 23 размеченных отрицательных примера. Для защиты нужны отдельные отложенные сценарии по всем трём группам. |
| Объяснять регулярность | API отдаёт `reasons` и историю платежей. Экран деталей использует первую причину в отдельных статусах. Этап 21 добавляет полный блок причин и интервалы списаний. |
| Показывать уверенность | API отдаёт `confidence` и `ml_probability`, в интерфейсе оценки нет. Этап 21. В ручном и отдельном trial-сценариях API заполняет `ml_probability` значением 1.0 без оценки классификатора. Для объяснения на экране учитывать источник оценки. |
| Без дублей при пересчёте | Два расчёта на одном входе вернули одинаковые 604 строки кэша, действия сохранились. Подтверждён другой путь к дублю: ручное добавление Skillbox к профилю с уже найденным Skillbox даёт две записи в витрине. |
| Прогноз следующего списания | Прогноз есть, API отдаёт дату, фронт её использует. Проверить демонстрационные случаи со сдвигом даты и концом месяца. |
| Предупреждать о росте цены и конце пробного периода | Оба сигнала рассчитываются и показываются на экране уведомлений. Trial — эвристика по символическому списанию и справочнику, с симуляционной датой. |
| Витрина с суммой, датой и историей цены | Есть список и детали с графиком. API хранит отдельные платежи, график группирует историю по месяцу. |
| Добавить, скрыть, отклонить ошибочную находку | Есть в API и UI. Ручное добавление с тем же именем обновляет ручную строку на уровне API. |
| Исправить подписку | Полноценной правки автонаходки, сброса или формы редактирования нет. Этап 22. Проверить, что правка видна в витрине, аналитике и уведомлениях и переживает пересчёт. |
| Граница функциональности | Действия меняют локальную витрину. Отмена подписки у внешнего провайдера вне кейса. |

## Локальная проверка 25 ноября

- `npm run lint` и `npm run build` прошли с локальным адресом API при сборке. Сценарии UI проверены по коду, браузерный прогон ещё нужен.
- В изолированной копии на Python 3.13 с локально подключённым OpenMP сгенерированы 112 162 операции для 159 профилей, обучена модель и запущен скрипт постобработки. Результат — 10 из 10 штатных сценариев. API подтвердил уведомления о росте цены и trial, добавление, скрытие и отклонение. Для повтора изменено время файла транзакций, чтобы обойти проверку свежести кэша и реально запустить расчёт.
- Сквозной расчёт нашёл 604 из 693 размеченных подписок (~87%) на той же синтетике, где обучалась модель, и пропустил 89. Это диагностический прогон. Для сравнения, оценка классификатора в обучающем скрипте считается на уже отобранных кандидатах. Для заявления о качестве нужно измерение всего пайплайна на отдельных данных, с разбором потерь на этапе отбора и детекции.

## Что должно быть в итоговой презентации

Список по слайду 15 материалов открытия. Слайды — обязательный итоговый материал. Видео демонстрации и дополнительные материалы — по необходимости.

1. **Концепция цифрового решения.** Помощник в мобильном банке выводит вероятные подписки из тестовой истории операций и помогает заранее заметить важное списание.
2. **Владелец и заказчик.** Т-Банк. Описать пользу для банка и клиента и обозначить место сервиса в банковском приложении.
3. **Целевая аудитория и роли.** Основной пользователь — клиент банка с несколькими регулярными подписками. Для показа подготовить профили с разными проблемами.
4. **Ключевые функции.** Поиск и объяснение, уверенность, прогноз даты, рост цены и trial, витрина и управление находками.
5. **Анализ аналогов и возможные преимущества.** Сравнить предложения по наблюдаемым сценариям и источникам данных. Подтвердить заявленные отличия.
6. **Концепция дизайна и интерфейса.** Показать мобильный путь пользователя от витрины до объяснения и действия, обосновать информационную иерархию.
7. **Прототип.** Минимум — кликабельный интерфейс. Цель команды — работающий веб-прототип с серверным расчётом, коротким живым демо и запасной записью.
8. **Ресурсы для полноценного прототипа.** Оценить сроки, оборудование и инфраструктуру, роли и компетенции, данные для проверки качества.
9. **Как работала команда.** Показать технологии и почему их выбрали, инструменты управления проектом, роли, план, выполненные и оставшиеся задачи. Указать применимость Битрикс24 и вклад текущей итерации.
10. **Отношение к проекту и продолжение.** Описать готовность развивать решение и конкретный следующий этап, включая проверку качества на более разнообразных данных.

## Предлагаемый порядок до защиты

1. **25–26 ноября.** Сверить состав и параллельную работу с командой, решить судьбу PR № 1, зафиксировать воспроизводимый запуск, проверить сценарии роста цены, trial и сложных отрицательных примеров.
2. **26–28 ноября.** Закрыть этап 21. Вывести понятную оценку уверенности и причины, показать даты/суммы платежей и интервалы. Параллельно собрать первый вариант презентации и сравнение аналогов.
3. **28–30 ноября.** Закрыть этап 22. Дать изменить и сбросить поля, проверить сохранение правок при реальном пересчёте и отсутствие дублей между источниками. Дать команде повторить демо на фиксированных данных.
4. **30 ноября — 1 декабря.** Поднять стабильный демо-адрес или подготовить локальный показ, записать запасное видео, пройти весь сценарий и отрепетировать питч на 5 минут. Для показа выбрать рост цены, trial, ошибочную находку или исправление с пересчётом.
5. **2 декабря.** Защита. Отдельно подготовить ответы по качеству на синтетике, отличию от простого поиска периодических платежей и границам интеграции с банком.
