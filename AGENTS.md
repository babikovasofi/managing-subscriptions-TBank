# AGENTS.md

Этот файл — главный источник контекста для любого агента, работающего над проектом (Codex, Claude Code и др.).
`CLAUDE.md` только импортирует этот файл. Правки вносим сюда, не в `CLAUDE.md`.
Перечитывай его в начале каждой сессии и сверяйся с разделом «Прогресс» перед стартом задачи.

---

## 1. О проекте

Хакатон Т-Банка (программа ТОПИТ), кейс «Управление подписками». Вторая итерация: код первой итерации (этапы 0–20) уже в репо, кейс немного изменился.

**Что делаем:** сервис, который по тестовой истории операций находит вероятные подписки, объясняет найденную регулярность, показывает уверенность, прогнозирует следующую дату списания и предупреждает о росте цены и окончании пробного периода. Витрина подписок (сумма, дата, история цены) + серверный модуль регулярности.

**Что показываем жюри:** публичный веб-сайт, имитирующий экран мобильного приложения Т-Банка, с реально работающим ML-ядром на синтетических данных. Жюри переключаются между клиентами и видят живой продукт. Ссылка на демо — главный артефакт.

**Команда:** 2 человека, оба работают и с ML/бэком, и с фронтом. Агенты: Codex и Claude Code — оба читают этот файл.

**Срок:** 7 дней.

## 3. Правила работы агента

- **Декомпозируй** каждую задачу перед началом. Показывай план шагов, жди подтверждения если шаги нетривиальны.
- **Пиши чистый код**: типизация (Python type hints, TypeScript строгий), осмысленные имена, без магических чисел (выноси в константы/конфиг), комментарии только там, где логика неочевидна.
- **Проверяй работоспособность перед коммитом**: запусти скрипт/сервис, прогони sanity-checks, убедись что предыдущая функциональность не сломана.
- **Конвенциональные коммиты**: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `test:`, `style:`. Сообщения на английском, коротко и по делу.
- **Не принимай архитектурных и продуктовых решений сам**. Если развилка — спроси.
- **Спрашивай если не уверен**: имя переменной, структура файла, выбор библиотеки, формат данных, граничный случай в логике. Лучше задать вопрос, чем переделывать.
- **Обновляй раздел «Прогресс»** после каждой завершённой задачи: меняй статус `[ ]` → `[~]` (в работе) → `[x]` (готово).
- **Если хочешь добавить или изменить что-то в AGENTS.md — сначала спроси пользователя**.
- **Не делай ничего из раздела «Что НЕ делаем»**.

### Цикл задачи

Каждый этап проходит строго по шагам через скиллы харнесса (раздел «Харнесс» ниже). Следующий шаг — только после предыдущего.

1. **План** — скилл `plan`: сабагенты `planner` + `skeptic` пишут `swarm-report/<slug>-plan.md` с критериями готовности (берутся из «Готово, когда» этапа).
2. **Согласование.** Покажи план и блокеры пользователю. Без его «ок» код не пишешь.
3. **Билд** — скилл `build`: исполнители по зонам файлов реализуют план и прогоняют проверки. Отклонение от плана — снова к пользователю.
4. **Ревью** — скилл `review`: сабагент `reviewer` в чистом контексте сверяет diff с планом, постановкой и «Что НЕ делаем». `rework` → скилл `debug` или повтор `build`.
5. **Коммит и пуш.** Только если ревью `ship` и пользователь согласен. Обнови «Прогресс» (`[x]`), закоммить, запушь.

Мелочь (опечатка, одна строка) — без `plan`, но ревью и «ок» пользователя перед коммитом всё равно.

Память между сессиями — этот файл («Прогресс», «Открытые вопросы»), `docs/history.md` и `swarm-report/`. Своей внутренней памяти агента не доверяй: что не записано здесь, следующая сессия не узнает.

### Протокол синхронизации между сессиями

Команда работает по очереди в одной ветке через `git pull` → работа → `git push`. Между сессиями меняется и человек, и агент. Чтобы следующая сессия не теряла контекст:

- **В начале каждой сессии**: прочитай AGENTS.md целиком, особенно разделы «Прогресс» и «Открытые вопросы». Спроси у пользователя сделан ли `git pull`, если не уверен.
- **Перед стартом задачи**: поставь её статус `[~]` в разделе «Прогресс» и сделай коммит `chore: start <task name>`. Так следующая сессия сразу видит над чем работали.
- **После завершения задачи**: поставь `[x]`. Если по ходу появились важные решения, нюансы или новые ограничения — запиши их в «Открытые вопросы» или (с согласия пользователя) в соответствующий раздел AGENTS.md.
- **Если задача оставлена недоделанной**: оставь `[~]` и добавь в разделе «Прогресс» короткую заметку прямо под пунктом — что сделано, что осталось, где остановился, какие файлы трогал. Пример:
  > `[~] Генератор датасета`
  > _Сделано: архетипы персон и 140 случайных клиентов. Осталось: 10 режиссированных клиентов и sanity-checks. Файл `data/generator/generate.py`, функция `generate_scripted_clients()` — заглушка._
- **Перед редактированием файлов**: убедись что pull сделан (спроси пользователя).
- **В конце сессии**: обнови статусы, закоммить, запушь.

## 6. Контракты между модулями

- **Транзакции (CSV):** `transaction_id, client_id, date, amount, merchant_name, mcc_code, category, description`
  - `date` в формате ISO 8601 (YYYY-MM-DD HH:MM:SS)
  - `amount` в рублях, отрицательные = списания, положительные = поступления
  - `category` — категория мерчанта (см. п. 8)
- **Ground truth (CSV):** `client_id, merchant_name, is_subscription, true_period_days, true_amount, scenario_tag`
  - `scenario_tag`: `regular`, `price_increase`, `trial_period`, `abandoned`, `false_positive_trap`
- **API → фронт:** JSON по схеме из `docs/api_contract.md` (создаётся на этапе бэка)

## 7. ML-подход

**Гибрид rule-based + ML-классификатор:**

1. **Этап 1 — rule-based отбор кандидатов.** Группируем транзакции клиента по мерчанту, считаем фичи (число транзакций, средний интервал, дисперсия интервала, стабильность суммы, MCC, наличие в словаре подписочных сервисов). Отсекаем явно не-подписки (одна транзакция, продукты, кафе, переменные суммы).
2. **Этап 2 — ML-классификатор** (LightGBM) выдаёт вероятность «подписка» на пуле кандидатов. Порог настраивается по precision/recall на ground truth.
3. **Этап 3 — постобработка.** Каждой найденной подписке присваивается статус и метаданные.

**Объяснимость обязательна** (слайд: «объяснять найденную регулярность, показывать уверенность»): для каждой подписки сохраняем причины классификации (интервал, стабильность суммы, категория) и показываем их пользователю.

### Определения статусов

- **active** — регулярные списания, нет аномалий.
- **price_increased** — медиана последних 3 платежей ≥ 15% выше медианы первых 3 платежей, либо ≥ 50₽ абсолютный рост при медиане < 500₽. При n < 6 платежей — fallback: последний платёж vs медиана предыдущих.
- **possibly_unused** — только для категории `gaming` (высокая уверенность): подписка существует ≥ 3 месяца И за последние 3 месяца у клиента нет транзакций других gaming-мерчантов. Для всех остальных категорий статус не выставляется — без надёжного активностного сигнала рекомендацию не делаем.
- **trial_ending** — первое полное списание ожидается в ближайшие 7 дней после символического (< 10₽) платежа того же мерчанта. Два канала обнаружения: (1) нормальный пайплайн для n ≥ 3; (2) `detect_pending_trials` — отдельный проход до rule-based+ML, для n < 3 по справочнику подписок.

Один статус на подписку. Приоритет: `trial_ending` > `price_increased` > `possibly_unused` > `active`.

## 9. Параметры датасета (зафиксировано)

- **159 клиентов:** 140 случайных + 19 режиссированных (10 демо-сценариев + 9 hard-negative клиентов для качества ML).
- **12 месяцев истории** транзакций.
- **~60 транзакций на клиента в месяц** (разброс 30–100 в зависимости от персоны).
- **~110 000 строк** итого.
- **8–10 архетипов персон**: студент, фрилансер, семейный, геймер, "забывашка", IT-специалист, пенсионер с цифровыми привычками, минималист, заядлый стример, активный пользователь подписочных сервисов.
- **simulation_today**: фиксированная дата «сегодня» в датасете (например, последний день генерации). Хранится в `data/output/meta.json`. Весь фронт и API работают относительно неё.
- **random_seed**: фиксированный (например, 42), вынесен в конфиг генератора.

### Режиссированные клиенты (19 штук)

**Демо-сценарии (scripted_01–10):**
1. Явный рост цены подписки (Кинопоиск 299→399₽).
2. Пробный период заканчивается через 2 дня.
3. Заброшенный gaming (VK Play Cloud, покупок игр нет 4 месяца).
4. «Тяжёлый случай»: 8+ подписок, >5000₽/мес.
5. Новичок: 1–2 подписки, простой кейс.
6. Несколько подписок с пересекающимися датами списания (стресс на UI).
7. Бывший пользователь: 6 месяцев был активен, последний месяц без подписок.
8. Дублирующиеся подписки (Яндекс.Музыка + VK Музыка — рекомендация подумать).
9. Ложный положительный triger: абонемент в зал — модель должна правильно отделить.
10. Семейный план: одна подписка покрывает нескольких — проверить что не дублируется.

**Hard-negative клиенты (scripted_11–19):** Арендаторы, ипотечники, BNPL, репетиторы, фитнес — регулярные платежи НЕ-подписки, проходящие rule-based фильтр. Нужны для качества ML: без них негативов через фильтр проходило только 20 (→ 48 после добавления). Используются только при обучении, не показываются в демо.

## 10. Аналитика и рекомендации (реализовано в первой итерации)

Для каждого клиента отдаём:

- **Общая сумма подписок в месяц.**
- **Топ-3 самых дорогих подписки.**
- **Список подписок со статусом `possibly_unused`** с указанием уверенности и причины.
- **Потенциальная экономия** = сумма подписок со статусом `possibly_unused` (high confidence).
- **Объяснение для каждой рекомендации**: почему модель так считает.

**Тон рекомендаций:** не навязчивый. Формулировки в стиле «Возможно, вам стоит проверить эту подписку», а не «Отключите её срочно».

## 11. Уведомления (реализовано в первой итерации)

Реальные push не шлём. Делаем экран «Уведомления» внутри приложения со сгенерированным списком.

Триггеры:
- За 1–3 дня до ближайшего списания.
- После окончания пробного периода (ожидается первое платное списание).
- Рост стоимости подписки.
- Сводка: «Вы платите за N подписок, общая сумма — X ₽/мес».

Каждое уведомление содержит: дату, текст, тип, ссылку на подписку.

## 12. Действия пользователя (реализовано в первой итерации)

В MVP пользователь может:
- Отметить подписку как важную (`mark_important`).
- Отключить уведомления по конкретной подписке (`mute_notifications`).
- Пометить подписку как ошибочно определённую (`mark_false_positive`).
- Вручную добавить подписку (`add_manual`).
- Скрыть подписку (`hide`).

Хранятся в SQLite, таблица `user_actions(client_id, merchant_name, action_type, created_at)`.
При формировании ответа API: подписки из кэша ML + наложенные действия пользователя.

**Решение (вторая итерация):** слайд требует «добавить, скрыть, исправить, отклонить». Добавить = `add_manual`, скрыть = `hide`, отклонить = `mark_false_positive` — есть. «Исправить» нет — это этап 22. `mark_important` и `mute_notifications` оставляем как есть (работают, слайду не противоречат), но не развиваем и в демо не выпячиваем.

## 13. Кэширование ML-результатов

ML-пайплайн прогоняется **один раз** при старте API (или скриптом инициализации БД).
Результаты пишутся в таблицу `subscriptions_cache(client_id, merchant_name, status, confidence, next_payment_date, amount, category, reasons_json, ...)`.
При запросе фронт получает union: кэш + пользовательские действия.

Это даёт быстрый ответ API и осмысленное использование SQLite.

## 14. Что НЕ делаем (явный список)

- **Не отменяем подписку у внешнего поставщика.** Только показываем, предупреждаем и даём пользователю управлять витриной.
- **Не отправляем реальные push-уведомления** (только экран внутри приложения).
- **Не делаем регистрацию/логин/авторизацию** (выбор клиента через переключатель в демо).
- **Не делаем годовые подписки** (только месячные/недельные; для годовых 12 месяцев истории мало).
- **Не делаем интеграцию с реальным API Т-Банка**.
- **Не выходим за рамки постановки и списка этапов.** Никаких дополнительных «фишек» без согласования.

## 15. Деплой

**Где:** Яндекс Облако, одна ВМ, Ubuntu 22.04, **не прерываемая** (preemptible = off). Публичный IP.

**Как:** Docker Compose, три сервиса:
- `api` — существующий `Dockerfile` в корне репо (FastAPI, порт 8000; при сборке генерирует датасет, обучает модель, заполняет БД).
- `web` — Next.js (`web/`). `NEXT_PUBLIC_API_URL` передаётся **при сборке** (build arg), т.к. Next.js вшивает `NEXT_PUBLIC_*` в бандл.
- `caddy` — reverse proxy с автоматическим HTTPS через домен `<ip>.sslip.io` (IP ВМ с точками, например `51.250.1.2.sslip.io`). Отдаёт `web`, проксирует API.

**Обновление:** на ВМ `git pull && docker compose up -d --build`.

Railway (первая итерация) больше не используем.

## 16. Что уже реализовано (этапы 0–20)

Подробно, с заметками — в `docs/history.md`.

- Справочники мерчантов: 30 российских подписочных сервисов в 9 категориях + ≥30 обычных мерчантов (`data/references/`).
- Генератор синтетики: 159 клиентов, 12 месяцев, ~110k транзакций, 10 демо-сценариев + 9 hard-negative (аренда, ипотека, BNPL, репетиторы, фитнес) (`data/generator/`).
- ML: фичи + rule-based отбор + LightGBM (`ml/`), метрики в README.
- Постобработка: статусы `active` / `price_increased` / `possibly_unused` / `trial_ending`, дата следующего списания, причины (`reasons`).
- Аналитика и уведомления: сумма/мес, топ-3, экономия, тексты уведомлений.
- API (FastAPI + SQLite): кэш ML-результатов, user_actions (важная, mute, ошибочная, скрыть, вручную), контракт в `docs/api_contract.md`.
- Фронт (Next.js): переключатель клиентов, экраны подписок, деталей, аналитики, уведомлений, ручного добавления.

## 17. План работы (для агента)

Этот план — основной маршрут. Двигайся по нему сверху вниз. Каждый этап = одна или несколько задач из раздела «Прогресс». Этапы 0–20 — в `docs/history.md`.

### Этап 21. Уверенность в % и блок «Почему это подписка»
**Что сделать:** в карточке/деталях подписки показать уверенность в процентах (из `ml_probability`) и блок «Почему это подписка»: все причины из `reasons` + таймлайн платежей (даты и суммы из `price_history`) с интервалами в днях между соседними платежами. Если нужно новое поле в API — сначала обновить `docs/api_contract.md`.
**Готово, когда:** у `scripted_01` в деталях видно «Уверенность NN%», список всех причин и таймлайн, где между платежами подписан интервал (≈30 дн.); у ручной подписки (`is_manual`) блок не ломается (100%, одна точка без интервала); `npm run build` без ошибок.

### Этап 22. «Исправить подписку»
**Что сделать:** пользователь правит найденную подписку: сумму, период, дату следующего списания, категорию. Правка хранится в SQLite отдельно от кэша ML и накладывается поверх него при ответе API (как user_actions). Повторный расчёт (`python -m api.init_db`) правку не теряет и дубликатов не создаёт. Ручные подписки тоже можно исправить. Сначала — эндпоинт и поля в `docs/api_contract.md` (например флаг `is_edited`), потом бэк, потом форма на экране деталей. Сброс правки к значениям ML.
**Готово, когда:** у `scripted_01` правка суммы и даты видна в карточке, деталях, сумме за месяц и уведомлениях; после повторного `init_db` правка на месте и подписка одна; сброс возвращает значения ML; невалидный ввод (сумма ≤ 0, период вне 1–366) → `400`; `npm run build` без ошибок.
