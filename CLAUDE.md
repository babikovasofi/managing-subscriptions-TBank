## 1. О проекте

Хакатон Т-банка, кейс «Управление подписками».

**Что делаем:** MVP сервиса для мобильного приложения банка, который автоматически находит подписки клиента в истории транзакций, показывает аналитику, предупреждает о списаниях и помогает находить лишние подписки.

**Что показываем жюри:** публичный веб-сайт, имитирующий экран мобильного приложения Т-банка, с реально работающим ML-ядром на синтетических данных. Жюри переключаются между клиентами и видят живой продукт. Ссылка на демо — главный артефакт.

**Команда:** 2 человека, оба работают и с ML/бэком, и с фронтом.

**Срок:** 1.5 дня.

## 6. Контракты между модулями

- **Транзакции (CSV):** `transaction_id, client_id, date, amount, merchant_name, mcc_code, category, description`
  - `date` в формате ISO 8601 (YYYY-MM-DD HH:MM:SS)
  - `amount` в рублях, отрицательные = списания, положительные = поступления
  - `category` — категория мерчанта (см. п. 8)
- **Ground truth (CSV):** `client_id, merchant_name, is_subscription, true_period_days, true_amount, scenario_tag`
  - `scenario_tag`: `regular`, `price_increase`, `trial_period`, `abandoned`, `false_positive_trap`
- **API → фронт:** JSON по схеме из `docs/api_contract.md` (создаётся на этапе бэка)

## 7. ML-подход

**Гибрид rule-based + ML-классификатор:**

1. **Этап 1 — rule-based отбор кандидатов.** Группируем транзакции клиента по мерчанту, считаем фичи (число транзакций, средний интервал, дисперсия интервала, стабильность суммы, MCC, наличие в словаре подписочных сервисов). Отсекаем явно не-подписки (одна транзакция, продукты, кафе, переменные суммы).
2. **Этап 2 — ML-классификатор** (LightGBM) выдаёт вероятность «подписка» на пуле кандидатов. Порог настраивается по precision/recall на ground truth.
3. **Этап 3 — постобработка.** Каждой найденной подписке присваивается статус и метаданные.

**Объяснимость обязательна** (требование ТЗ): для каждой подписки сохраняем причины классификации (интервал, стабильность суммы, категория) и показываем их пользователю.

### Определения статусов

- **active** — регулярные списания, нет аномалий.
- **price_increased** — последнее списание ≥ 15% выше медианы предыдущих, либо ≥ 50₽ роста для подписок < 500₽.
- **possibly_unused** — гибридный критерий:
  - Для категорий с сопутствующими тратами (gaming, food_delivery, education): подписка существует ≥ 3 месяца И за последние 3 месяца нет связанных транзакций в этой категории.
  - Для остальных категорий: подписка существует ≥ 6 месяцев (низкая уверенность, явно помечаем).
  - Поле `confidence`: `high` / `low` — для честности перед пользователем.
- **trial_ending** — первое полное списание ожидается в ближайшие 7 дней после серии нулевых/символических (< 10₽) платежей того же мерчанта.

Один статус на подписку. Приоритет: `trial_ending` > `price_increased` > `possibly_unused` > `active`.

## 9. Параметры датасета (зафиксировано)

- **150 клиентов:** 140 случайных + 10 режиссированных под демо-сценарии.
- **12 месяцев истории** транзакций.
- **~60 транзакций на клиента в месяц** (разброс 30–100 в зависимости от персоны).
- **~110 000 строк** итого.
- **8–10 архетипов персон**: студент, фрилансер, семейный, геймер, "забывашка", IT-специалист, пенсионер с цифровыми привычками, минималист, заядлый стример, активный пользователь подписочных сервисов.
- **simulation_today**: фиксированная дата «сегодня» в датасете (например, последний день генерации). Хранится в `data/output/meta.json`. Весь фронт и API работают относительно неё.
- **random_seed**: фиксированный (например, 42), вынесен в конфиг генератора.

### Режиссированные клиенты (10 штук)

1. Явный рост цены подписки (Кинопоиск 299→399₽).
2. Пробный период заканчивается через 2 дня.
3. Заброшенный Steam (подписка есть, покупок игр нет 4 месяца).
4. «Тяжёлый случай»: 8+ подписок, >5000₽/мес.
5. Новичок: 1–2 подписки, простой кейс.
6. Несколько подписок с пересекающимися датами списания (стресс на UI).
7. Бывший пользователь: 6 месяцев был активен, последний месяц без подписок (показать что система не ругается).
8. Дублирующиеся подписки (Яндекс.Музыка + VK Музыка — рекомендация подумать).
9. Ложный положительный triger: ежемесячная одинаковая сумма НЕ-подписке (например, абонемент в зал) — модель должна правильно отделить.
10. Семейный план: одна подписка покрывает нескольких — проверить что не дублируется.

## 10. Аналитика и рекомендации (требование ТЗ)

Для каждого клиента отдаём:

- **Общая сумма подписок в месяц.**
- **Топ-3 самых дорогих подписки.**
- **Список подписок со статусом `possibly_unused`** с указанием уверенности и причины.
- **Потенциальная экономия** = сумма подписок со статусом `possibly_unused` (high confidence).
- **Объяснение для каждой рекомендации**: почему модель так считает.

**Тон рекомендаций:** не навязчивый. Формулировки в стиле «Возможно, вам стоит проверить эту подписку», а не «Отключите её срочно».

## 11. Уведомления (требование ТЗ)

Реальные push не шлём. Делаем экран «Уведомления» внутри приложения со сгенерированным списком.

Триггеры (из ТЗ):
- За 1–3 дня до ближайшего списания.
- После окончания пробного периода (ожидается первое платное списание).
- Рост стоимости подписки.
- Сводка: «Вы платите за N подписок, общая сумма — X ₽/мес».

Каждое уведомление содержит: дату, текст, тип, ссылку на подписку.

## 12. Действия пользователя (требование ТЗ)

В MVP пользователь может:
- Отметить подписку как важную (`mark_important`).
- Отключить уведомления по конкретной подписке (`mute_notifications`).
- Пометить подписку как ошибочно определённую (`mark_false_positive`).
- Вручную добавить подписку (`add_manual`).
- Скрыть подписку (`hide`).

Хранятся в SQLite, таблица `user_actions(client_id, merchant_name, action_type, created_at)`.
При формировании ответа API: подписки из кэша ML + наложенные действия пользователя.

## 13. Кэширование ML-результатов

ML-пайплайн прогоняется **один раз** при старте API (или скриптом инициализации БД).
Результаты пишутся в таблицу `subscriptions_cache(client_id, merchant_name, status, confidence, next_payment_date, amount, category, reasons_json, ...)`.
При запросе фронт получает union: кэш + пользовательские действия.

Это даёт быстрый ответ API и осмысленное использование SQLite.

## 15. План работы (для агента)

Этот план — основной маршрут. Двигайся по нему сверху вниз. Каждый этап = одна или несколько задач из раздела «Прогресс».

### Этап 0. Инициализация
Создать структуру репозитория, базовые конфиги (pyproject.toml/requirements.txt, package.json для Next.js), .gitignore, README.md заглушка. Скопировать ТЗ в `docs/TZ.md`. Инициализировать git, сделать первый коммит.

### Этап 1. Справочники мерчантов
Создать два JSON-файла в `data/references/`:
- `subscriptions.json` — реальные российские подписочные сервисы. Поля: `name`, `category`, `base_price_rub`, `period_days`, `mcc_code`, `popularity` (0–1, для распределения). Минимум 30 сервисов, покрывающих все 9 категорий.
- `regular_merchants.json` — НЕ-подписочные мерчанты для шумового фона. Поля: `name`, `category` (food/transport/entertainment/etc), `mcc_code`, `typical_amount_range`, `frequency_per_month`. Минимум 30 сервисов.

Источник: общие знания о популярных в России сервисах. Цены — близкие к реальным на 2025–2026.

### Этап 2. Генератор датасета
Скрипт `data/generator/generate.py`. На вход: справочники, конфиг (число клиентов, период, seed, simulation_today). На выход: `transactions.csv`, `labels.csv`, `meta.json` в `data/output/`.

Логика:
1. Загрузить справочники.
2. Определить 10 архетипов персон (что покупают, какие подписки, сколько тратят).
3. Сгенерировать 140 случайных клиентов: распределить по архетипам, для каждого — набор подписок и шумовой фон.
4. Сгенерировать 10 режиссированных клиентов по сценариям из п. 9.
5. Для каждой подписки: серия списаний с jitter ±2 дня, шум по сумме, иногда повышение цены, иногда пробный период (0₽ или 1₽ на старте).
6. Для шумового фона: распределения по персоне, реалистичные паттерны (продукты чаще, такси реже).
7. Параллельно писать ground truth в `labels.csv`.
8. Sanity-checks в конце: каждый клиент имеет ≥ 1 подписку или явный кейс «нет подписок», все режиссированные клиенты на месте, нет транзакций в будущем относительно simulation_today.

### Этап 3. Фичи и rule-based отбор
Модуль `ml/features/extract.py` — извлекает фичи по группам (client_id, merchant_name): число транзакций, медианный интервал, дисперсия интервала, медианная сумма, коэффициент вариации суммы, наличие в словаре подписок, MCC-категория, длительность истории.
Модуль `ml/models/rule_based.py` — отбирает кандидатов в подписки (фильтр по числу транзакций ≥ 3, интервалу в разумных пределах, стабильности суммы).

### Этап 4. ML-классификатор
Модуль `ml/models/classifier.py` — обучает LightGBM на фичах с разметкой из ground truth. Train/test split по клиентам (не по транзакциям). Метрики: precision, recall, F1 на тесте. Сохранение модели в `ml/models/saved/model.pkl`.

### Этап 5. Постобработка и статусы
Модуль `ml/pipeline/postprocess.py` — для каждой подписки определяет статус (active / price_increased / possibly_unused / trial_ending) по правилам из п. 7, считает дату следующего списания, формирует список причин (для объяснимости).

### Этап 6. Полный ML-пайплайн
`ml/pipeline/run.py` — вход: путь к транзакциям, выход: список подписок со всеми атрибутами для всех клиентов. Этот вызов будет интегрирован в API.

### Этап 7. Аналитика
Модуль `ml/pipeline/analytics.py` — для каждого клиента считает: общую сумму/мес, топ-3, потенциальную экономию, генерирует тексты рекомендаций и уведомлений.

### Этап 8. API: схема ответа
`docs/api_contract.md` — фиксируем JSON-схему всех эндпоинтов до написания кода. После согласования — фронт может работать параллельно на моках.

Минимальный набор эндпоинтов:
- `GET /clients` — список клиентов для переключателя.
- `GET /clients/{id}/subscriptions` — список подписок.
- `GET /clients/{id}/analytics` — сводка.
- `GET /clients/{id}/notifications` — список сгенерированных пушей.
- `POST /clients/{id}/actions` — действие пользователя.
- `POST /clients/{id}/subscriptions/manual` — ручное добавление.

### Этап 9. API: реализация
FastAPI + SQLAlchemy + SQLite. Скрипт `api/init_db.py` — прогоняет ML-пайплайн на всём датасете и заполняет кэш. Эндпоинты возвращают данные согласно контракту, накладывают user_actions.

### Этап 10. Фронт: каркас и дизайн
Next.js App Router, Tailwind. Глобальные стили в духе Т-банка: жёлтый акцент, скруглённые карточки, тени. Адаптив под мобильный (max-width ~430px, тестируем на 375px). Главный layout — мобильный экран с верхней панелью и нижней навигацией.

### Этап 11. Фронт: переключатель клиентов
В шапке или отдельном экране — селектор клиента (для демо). Сохраняем выбранного клиента в LocalStorage. Все запросы идут с этим client_id.

### Этап 12. Фронт: экран подписок
Список карточек: иконка категории, название, сумма, дата следующего списания, бейдж статуса. Сверху — общая сумма за месяц.

### Этап 13. Фронт: экран деталей подписки
По тапу на карточку — детали: история списаний, объяснение статуса, действия (важная/скрыть/исправить).

### Этап 14. Фронт: экран аналитики
Топ-3 дорогих, потенциальная экономия, разбивка по категориям. Тон — мягкий, объяснимый.

### Этап 15. Фронт: экран уведомлений
Список сгенерированных пушей, отсортированный по дате.

### Этап 16. Фронт: ручное добавление подписки
Простая форма: название, сумма, период, категория. Сохраняется через API.

### Этап 17. Интеграция и тестирование
Запуск API + фронта локально, проход по всем сценариям с режиссированными клиентами. Фиксация багов.

### Этап 18. Деплой
API на Render/Railway, фронт на Vercel. Переменные окружения для URL API. Проверка по публичной ссылке.

### Этап 19. README и видео-демо
README с описанием проекта, ссылкой на демо, скриншотами, командами запуска. Скринкаст 30–60 сек обхода приложения.
